# Tokenizer 工作原理笔记

## Tokenizer 的数据结构：查找表

Tokenizer 由两部分静态数据组成：

### ① merges 表（几万~十几万行）

字节对 → 合并优先级：

```
("Ġt" + "he") → 排名 15
("th" + "e")  → 排名 82
...
```

### ② vocab 表（几万~十几万行）

token 字符串 → token ID：

```
"Ġthe"   → 123
"Ġhello" → 31373
...
```

**体积**: 1~5 MB（JSON 或二进制文件）

## Tokenizer 不是 AI 模型

| | Tokenizer | AI 模型（GPT、Claude） |
|---|---|---|
| **是什么** | 一本字典 + 分词规则 | 一个巨大的神经网络 |
| **大小** | 几 MB | 几百 GB - 几 TB |
| **能否浏览器跑** | ✅ | ❌ |
| **需要 GPU** | 不需要 | 需要 |
| **原理** | 查表匹配 | 矩阵运算推理 |
| **是否收费** | 免费开源 | 按 token 收费 |

## BPE 分词过程

```
输入: "hello world"
    ↓
① 正则匹配切初始块 → ["hello", " world"]
    ↓
② 字节编码 → [104, 101, 108, 108, 111, 32, 119, 111, 114, 108, 100]
    ↓
③ BPE 循环合并（按 merges 表优先级）
   每一步合并都是在查 merges 表，看哪一对优先级最高
   合到头了再查 vocab 表取 token ID
    ↓
输出: token ID 列表，如 [15496, 995]
```

全程就是**反复查表 + 合并**，没有任何"推理"发生。

## 为什么支持几十种 tokenizer 还不花钱？

### 方式一：WASM 编译（tiktoken 系）

- `openai/tiktoken` 有 Rust 实现 → 编译成 WASM（~2MB）
- 浏览器下载一次，本地执行

### 方式二：动态加载词汇表（HuggingFace 系）

- 每个 tokenizer 只需要 `tokenizer.json`（1-5MB）
- 浏览器动态加载到内存，本地用 JS/WASM 执行 BPE

## 每次都要重新执行 BPE 吗？

**是的，每次都从头跑。** 但这不是问题：

| 原因 | 说明 |
|------|------|
| **速度极快** | 几百字文本，BPE 只需几毫秒，缓存反而更慢 |
| **输入不同** | 几乎每次都不同，缓存命中率极低 |
| **表只加载一次** | merges 表和 vocab 表页面打开时加载一次，常驻内存 |

## 类比

Tokenizer 的本质是一本"字典" + "拼写规则"。

- **一次性**：下载字典（1-5MB）
- **每次**：对新文本查字典切词（毫秒级）

BPE 算法复杂度 O(输入长度)，无矩阵运算。几千字文本只需几到十几毫秒，比网络请求快得多。
