# 四种分词方法对比

主流子词分词方法一共有 4 种（GPT-1 那套已绝迹，不算在内）。

---

## 同一句话，四种切法

```
输入: "the lower the better"
```

| 方法 | 切分结果 | Token 数 |
|------|---------|:---:|
| BPE | `["the", " lower", " the", " better"]` | 4 |
| WordPiece | `["the", "low", "##er", "the", "better"]` | 5 |
| Unigram | `["the", " low", "er", " the", " better"]` | 5 |
| GPT-1 那套 | `["the", "lower", "the", "better"]` | 4 |

凭什么切出不同的结果？不是"切得好不好"，是**训练词表时，用什么标准决定合并哪一对**。

---

## BPE：谁出现次数多就合谁

```
训练语料: "low lower lowest lowing"

初始: {l, o, w, e, r, s, t, i, n, g}    10 个字节

统计相邻对频率:
  "l"+"o" 出现 4 次 ← 最高
  "o"+"w" 出现 4 次
  "w"+"e" 出现 1 次
  ...

合并 "lo": {lo, w, e, r, s, t, i, n, g}  9 个 token
再统计: "lo"+"w" 出现 4 次 ← 最高
合并 "low": {low, e, r, s, t, i, n, g}   8 个 token

...循环直到词表达到预设大小...
最终: {low, lower, lowest, lowing, ...}
```

**规则简单粗暴：谁出现次数多就合谁。** 不关心合完之后语言模型性能变好还是变差，只看频率。

---

## WordPiece：谁对语言模型贡献大合谁

```
同样训练语料: "low lower lowest lowing"

WordPiece 不直接数频率，而是算"合了之后，语言模型说这段话的概率增加了多少"。

"l"+"o" → "lo": 概率增益 +0.02
"o"+"w" → "ow": 概率增益 +0.05  ← 更高！合这个
"lo"+"w" → "low": 概率增益 +0.12 ← 更高！接着合

...循环直到词表达到预设大小...
```

**合并不看原始频率，看合完之后语言模型困惑度降了多少。** 这也是为什么 WordPiece 切出来的词带 `##` 前缀——`##er` 表示"er 是一个词中段，不是一个独立词"。

```
BPE:         lower → lo + wer         （不知道为什么这样切）
WordPiece:   lower → low + ##er       （## 标记词中段，清晰）
```

---

## Unigram（SentencePiece）：先全训再删

```
Unigram 和上面两种完全相反——不是从零开始往上加，而是先训一个大词表，再往下删。

步骤 1: 初始化 —— 把所有可能的子串都加进词表
  词表: {l, o, w, lo, ow, low, e, er, r, ...}  几千个候选

步骤 2: 算每个 token 的"损失" —— 删掉它，语言模型变差多少

步骤 3: 删掉损失最小的 10%

步骤 4: 重复步骤 2-3，直到词表缩小到目标大小

最终: {low, er, the, better, ...}
```

**不是"合并"，是"淘汰"——起点是超大词表，一步步砍掉最没用的。** 这也是为什么 Unigram 训练特别慢（每删一轮要重算全语料损失），但最终词表通常比 BPE 更干净。

---

## 四种方法的本质差异

| | BPE | WordPiece | Unigram | BBPE（BPE 进化版） | GPT-1 |
|---|---|---|---|---|---|---|
| 起点 | 256 个字节 | 所有字符 | 所有候选子串 | 256 个字节 | spaCy 词表 |
| 方向 | ↑ 往上加 | ↑ 往上加 | ↓ 往下删 | ↑ 往上加 | 先词后 BPE |
| 合并标准 | 频率 | 概率增益 | 删除损失 | 频率 | — |
| 有 OOV 吗 | ⚠️（字符级有） | ⚠️ | ✅ 无 | ✅ **绝对无** | ⚠️ 有 |
| 代表人物 | — | BERT 系列 | T5, Gemma | GPT 全家, Qwen, DeepSeek | GPT-1（已绝迹） |

## BBPE：BPE 的关键进化版

GPT-2 之后，BPE 做了一个关键改进——从"字符级"变成"字节级"，称为 **BBPE（Byte-level BPE）**。

### 为什么需要字节级

普通 BPE 在**字符（Unicode 码点）层面**操作：

```
输入: "café"
字符拆分: ["c", "a", "f", "é"]     ← é 是一个 Unicode 字符
BPE 合并: ["caf", "é"]              ← 正常

输入: "🚀"
字符拆分: ["🚀"]                    ← 只有 1 个字符，没法继续拆
BPE 合并: 无合并可能，1 个 token

但如果这个 emoji 不在词表里：
→ 崩溃或标为 <UNK>
```

BBPE 的解决方案：**不按字符拆，按字节拆。**

那 256 个基础 token 就是字面意义的 **0x00 到 0xFF**——UTF-8 编码后的每一个字节值：

```
0x00 → token ID 0      空字节 / 控制字符
0x20 → token ID 32     空格
0x41 → token ID 65     'A'
0x61 → token ID 97     'a'
0xE7 → token ID 231    UTF-8 里"猫"的第一个字节
...
0xFF → token ID 255    第 256 个
```

任何文本用 UTF-8 编码后都是一串 0~255 的数字，所以起点只要这 256 个，地球上所有文字都能被表示：

```
"hello" → [0x68, 0x65, 0x6c, 0x6c, 0x6f]           5 个基础 token
"你好"  → [0xe4, 0xbd, 0xa0, 0xe5, 0xa5, 0xbd]     6 个基础 token
"🚀"    → [0xf0, 0x9f, 0x9a, 0x80]                 4 个基础 token
```

BPE 算法从这 256 个出发，逐步把高频相邻对合并成大 token（"lo"、"er"、"ing"…）。词表里前 256 个 ID 永远是这组字节——地基，一条都不能删。

**那原版（字符级）BPE 的初始词表从哪来？**

不是从 Unicode 全集来——Unicode 有 15 万个字符，拿它当起点 BPE 不用训了。而是**训练语料里实际出现了哪些字符，就收哪些**：

```
训练语料: 一份中文维基百科 dump

实际出现的汉字: ~15,000 个（常用字 + 部分生僻字）
没出现的汉字: 剩下的 ~75,000 个（异体字、古字、日韩特有汉字）
加上英文大小写 + 数字 + 标点 ≈ 17,000 个

初始词表 = 这 17,000 个字符
BPE 从这里开始往上合并

用户之后输入 "𰻝"（一个没在语料里出现过的生僻字）:
  → 初始词表没有 → 合都没法合 → <UNK>
```

所以字符级 BPE 的盲区就是**训练语料覆盖不到的 Unicode 字符**。中文有九万多汉字，一份通用语料通常只覆盖一万多，剩下八万个全是盲区。这就是 GPT-2 回到字节级的根本原因——256 个字节覆盖 UTF-8 能表示的一切，不存在"某个字没在语料里出现过"的问题。

一个具体例子：

```
输入: "🚀"
UTF-8 编码: [0xF0, 0x9F, 0x9A, 0x80]    ← 4 个字节
BBPE 切分: ["ð", "Ł", "Ü", "Ć"]         ← 每个字节映射到一个 Unicode 显示字符
         (显示字符是 256+byte 映射出来的，实际代表的是原始字节)

输入: "hello"
UTF-8 编码: [0x68, 0x65, 0x6C, 0x6C, 0x6F]
BBPE 切分: ["h", "e", "l", "l", "o"]      ← ASCII 字符和字节一一对应
         (继续 BPE 合并...)
```

### 为什么这是关键改进

| 普通 BPE | BBPE |
|----------|------|
| 字符层面操作 | 字节层面操作 |
| Unicode 码点不超过 256 个时能处理 | **所有 Unicode 字符**都能处理 |
| 遇到罕见 emoji/符号 → `<UNK>` | 遇到罕见 emoji → 拆成 4 个字节，逐个编码 |
| 词表里没有的东西就是没有 | **永远不会有 OOV** |

### 一句日语展示

```
输入: "猫"（不在词表里）

普通 BPE:
  "猫" → 词表没有 → <UNK> → 信息丢失 ❌

BBPE:
  UTF-8: [0xE7, 0x8C, 0xAB]
  映射显示字符: ["ç", "ì", "«"]
  每个字节都在 256 基础 token 里 → 能编码 ✅
  
  如果语料中"猫"频繁出现，BPE 会把 ç+ì+« 合并成一个 token "猫"
  如果不频繁，就保持 3 个 token → 稍低效但完整
```

### 现在叫 BPE 的东西基本都是 BBPE

GPT-2 之后的"BPE"默认指 BBPE。Qwen / DeepSeek / Kimi 用的"Byte-level BPE"就是 BBPE。OpenAI、Llama 3+、MiniMax——全用这套。纯字符级 BPE 在 2019 年 GPT-2 发布后就被淘汰了。

### 字节→字符→字节：一段绕圈史

有意思的是，BBPE 其实是绕了一大圈回到原点。BPE 算法最初就工作在字节上：

```
1994  原始 BPE（Gage）        字节    数据压缩算法
2016  NLP 版 BPE（Sennrich）   字符    "我们把字节换成了字符" ← 引入 NLP
2019  BBPE（GPT-2）            字节    "我们把字符换回了字节" ← 回到原点
```

Sennrich 2016 年论文的原话：

> "Instead of merging frequent pairs of bytes, we merge characters or character sequences."

他把基本单位从字节换成字符，是因为当时 NLP 的语料小——字符级够用。但到了 GPT-2 时代，字符级的 OOV 问题（罕见 emoji、新 Unicode 字符无法编码）变得不可接受，于是 GPT-2 又换回字节——**但不是回到 1994 年的压缩算法，而是用 2016 年的 BPE 合并框架加上字节级起点。**

## 为什么推理阶段都一样

**训练方式不同，但推理阶段一律是查表。** 不管你是 BPE 训出来的词表还是 Unigram 删出来的词表——最终都是一本"token → ID"的字典。拿到文本后：

```
1. 拆成字节
2. 查词表：这个字节序列能匹配到哪个 token？
3. 输出 token ID
```

训练时 BPE/WordPiece/Unigram 争论了三四年。2023 年之后没人争论了——不是因为某种方法更好，是因为 ChatGPT 赢了，大家都跟着用 BPE 了。就像不是 TCP/IP 最优秀，但它是互联网的标准。
